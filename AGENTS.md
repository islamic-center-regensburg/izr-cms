# Project guide

This repository configures a Docker-based Directus 11.17.4 CMS backed by
PostgreSQL. See `README.md` for the data model, deployment, and access policies.

## Git workflow

- **Never commit directly to `dev` or `main`.** This applies to every change,
  however small, and to agents as well as people.
- Always create a new branch from an up-to-date `dev` (for example
  `feat/<topic>` or `fix/<topic>`) and do the work and the commits there.
- Make the commits on that branch with the `commit-changes` skill
  (`.agents/skills/tooling/commit-changes/`), which groups changes by topic and
  writes the messages.
- If the current branch is `dev` or `main` when a commit is about to be made,
  stop, create the branch first, then commit.
- Changes reach `dev` through a pull request (CI runs the smoke test on PRs to
  `dev` and `main`), and `main` only from `dev`.
- `.agents/skills` is the `belskills` git submodule: commit skill changes inside
  that repository first, then commit the updated submodule pointer here, on a
  branch as above.

## Layout

- `schemas/<domain>/`: one YAML collection per file (the data model, the only
  place it is edited). Project format, not a Directus snapshot.
- `revisions/NNNN_name/`: one folder per schema change: generated `schema.json`
  and `changes.json`, optional hand-written `up.sql` / `down.sql` (data only).
- `access/*.yaml`: managed policies, roles and service users (`screen`,
  `website`, `mcp`). Each user's token comes from the env variable named in
  `user.token_env`.
- `seeds/reference/` (always) and `seeds/examples/` (only `CMS_ENV=dev`).
- `scripts/`: the loader (`sync.js`, `schema-model.js`, `revisions.js`,
  `apply-policies.js`, `seed-data.js`), unit tests and `smoke-test.sh`. Extend
  these files; do not add loader modules.
- `tools/`: local helpers (`init-env.mjs`, `verify.mjs`, `revision.sh`,
  `revisions-cli.sh`), not in the image.
- `entrypoint.sh`: bootstrap, temporary server, `sync.js`, then the public server.
- Follows the `directus-backend-bootstrap` skill; compare with its `templates/`
  when changing the flow.

## Change safely

- Change the model only through YAML plus `make revision m="..."`. Never edit a
  revision that was applied anywhere; make a new one. Review every `-` line in
  `changes.json` (it loses data). `make check` must pass.
- Roll back with `make migrate-down` before deploying an older image.
- Seeds create only missing rows by stable key and never overwrite; changing a
  seed does not update existing installs (use `up.sql`). Translations are
  separate rows. Seeded collections use UUID keys.
- Money is an exact decimal in euros, never float or cents.
- Policies are owned by the YAML; do not edit managed users or policies in the
  UI. Keep least privilege; never commit tokens. Tokens: `SCREEN_TOKEN`,
  `WEBSITE_TOKEN`, `MCP_TOKEN` (32+ chars), generated by Terraform in `izr-infra`
  and passed to the CMS and the consuming app. The MCP user can only write draft
  news and events and never delete.
- Keep translations and language-specific slugs consistent; slug uniqueness per
  language is an application responsibility.
- Update the README in the same change as any schema, seed or access change.
- `make reseed CONFIRM=yes` destroys database and uploads. Never run it against
  data worth keeping; use a disposable Compose project (`-p`) for checks.

## Validation

- `npm test` runs the unit tests (no Docker).
- Isolated stack: a disposable project name and port, then
  `docker compose -p <tmp> --env-file .env up --build -d --wait`, `tools/verify.mjs`
  and `scripts/smoke-test.sh`, then `down -v` on that project only. In a dev
  container run the checks inside the directus container (copy `tools/` in).
- CI (`.github/workflows/smoke-test.yml`) runs unit tests, the smoke test,
  `check` and `verify` on every PR.
- `make up` rebuilds; `make restart` does not. Schema, revision, access, seed and
  script changes require a rebuild.
